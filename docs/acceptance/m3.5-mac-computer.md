# M3.5 attended Mac/Lima Computer acceptance

This is the owner-hardware lane for the Mac column of agent-computer spec §10.2,
plus the §11 item 4 narrowness amendment. It is deliberately absent from
`service-acceptance-realtiming`: hosted macOS runners do not prove nested Lima
`vz`, so a hosted run records every Mac row as a typed `NOT-RUN` and never as a
claim. Its Linux mirror is
[m3.5-linux-computer.md](m3.5-linux-computer.md); its transport-layer sibling,
which this lane assumes is already green on the same hardware, is
[m3-lima-transport.md](m3-lima-transport.md).

Everything below is driven through the shipped `wefty` CLI against real L1, L3,
agent and helper processes on the Mac Node, using one shared Lima VM and the same
digest-pinned reference Computer image the Linux lane uses. The only step that
talks to the helper directly is the independent removal inventory, and that step
says so.

## Standing prerequisites

**#394 is fixed (PR #407); the bridge is no longer a blocker.** On Lima `vz` the
gateway guard proves VM privacy through the guest default-route gateway with a
host-side floor refusing any host-owned address, and the capability-gated
host-loopback fallback *is* the transport — so Computer payloads reach
authoritative `Started` on a Mac. The Lima OCI transport lane
([m3-lima-transport.md](m3-lima-transport.md)) has since reached 31/34 PASS on
owner hardware, and rows that need a booted Computer can run.

What still gates rows:

- **The second physical tailnet device** (with its own Fabric identity and an
  `rfb-websocket-v1` client) **and the third no-grant identity** gate
  `mac.remote_takeover` and every row that says "with a watcher on the second
  device throughout". When they are absent, those assertions are typed `NOT-RUN`
  with reason `second_device_unavailable` naming the missing prerequisite —
  never PASS — and `destination.asserted` is false.
- **Plain Fabric identity fallback** records `dev.plain_fabric_identity` in
  `deviations`, as the Preconditions section already says.
- **#128 (headless cold reboot)** still owns `mac.create_boot`'s and
  `mac.reference_image_narrowness`'s headless halves.

`NOT-RUN` is not destination success. Do not fabricate a row; do not copy an
assertion from the Linux receipt.

## Preconditions

Everything [m3-lima-transport.md](m3-lima-transport.md) requires, including both
reference Computer image artifacts from the same `acceptance-image` run — and
those artifacts must actually be downloaded and extracted, not merely named.
Beyond that lane:

- **A second physical device on the owner's tailnet**, with its own Fabric
  identity and an RFB/WebSocket client that speaks `rfb-websocket-v1`. A phone or
  a second laptop both qualify. The destination sentence is about watching and
  driving the Computer from *that* device, never from the Mac running the Node.
- **A third Fabric identity with no grant** on the same tailnet, for the
  unauthorized-peer denial. A viewer whose grant was later revoked is a different
  proof and does not substitute.
- **Real Fabric identity** for L1's front door: persisted tsnet state, never an
  auth key in argv or a plist. If the owner tailnet is unavailable and the
  session falls back to plain identity, record
  `dev.plain_fabric_identity` in `deviations` — the rows may still pass, but
  `destination.asserted` is then forced false, because the sentence says
  *another tailnet device*.
- **Memory headroom facts.** VM memory is `min(25% of host RAM, 4 GiB)`. Record
  `host_memory_bytes` and `vm_memory_bytes`; the VM ceiling is what
  `mac.create_boot` latches against. Do not raise the cap to dodge the row.
- **Disk budget.** The 32 GiB VM disk must hold fully-allocated Computer disks
  plus backups, one clone and one custody export. Use 128 MiB Computer disks, as
  the Linux lane does, so the real ENOSPC arm stays reachable.
- **One host operator-mount root** for the custody export path, and `sudo` for
  exactly one step: unloading the agent LaunchDaemon before the independent
  removal inventory.

## Rows

Each row records its own `assertions` (measured), `attested` (recorded by hand),
`evidence`, and, when it is not PASS, `gaps`, `not_run_issue` and `reason`. Where
an assertion is the owner's own observation from the second device, set
`evidence["attestation"] = "human"`. A scripted RFB client that captures a
pointer-history comparison is a stronger and welcome substitute — record
`"scripted"` — but v1 does not require it.

### `mac.create_boot` — Create and boot

`wefty services create` without `--computer` must be refused. Create with
`--computer`, wait for both named endpoints published and
`AppliedRevision == IntentRevision`, inspect the guest-native disk image for full
allocation, then create Computers until the VM memory ceiling latches.

Assertions: `trait_only_refusal_observed`, `trait_only_publication`
(`published_port` is null), `fully_allocated_disk_on_disk`,
`view_named_endpoint_dialed`, `control_named_endpoint_dialed`,
`single_shared_vm` (one `limactl list` instance across every Computer — there is
no micro-VM-per-Computer claim), `cap_sum_latched`.
Evidence: `host_memory_bytes`, `vm_memory_bytes`, `cap_sum_bytes`,
`next_restart_at` (null), `last_failure.node_id`, and the bounded resource facts.

### `mac.network_egress` — Private network outbound

From inside the Computer: default route, public IPv4 connect, DNS resolve, and
the helper HTTP marker through the veth. Then probe the macOS **LAN** address and
`host.lima.internal` directly.

Assertions: the Linux set, plus `macos_lan_address_refused` and
`host_lima_internal_refused_outside_bridge`. The Mac has a second boundary the
Linux lane has no analogue for; prove the Computer cannot cross it.

### `mac.screen_crossover_refused` — Screen crossover refused

Two Computers in the one VM. From Computer A dial B's view, control and egress
addresses while B is provably alive to the relay.

Evidence keys mirror `linux.screen_crossover_refused`: refusal outcome and errno
for each dial, target liveness before, during and after, relay cleanup, and the
target's own loopback still working afterwards.

### `mac.remote_takeover` — Remote take-over

**From the second physical tailnet device:** grant `view` and watch; attempt
`take` and see it refused; grant `control`, take, release; admin override; revoke
while the viewer is driving; then have the third, ungranted identity attempt
`view`.

Assertions: `view_admission_live_second_device`, `view_only_take_refused`,
`view_pointer_isolation_live`, `unauthorized_peer_denied`, `cli_take_live`,
`cli_release_live`, `admin_override_live`, `revoked_while_driving`,
`revocation_closed_session`, and the five `audit_tail_*` kinds.
Evidence: viewer, admin and unauthorized Fabric user and device IDs, policy
revision, authority generation, and `takeover_end_to_end_ms` — recorded as a
fact, never compared to a threshold.

### `mac.restart_survival` — Restart survival

Kill the payload, kill the shim, kill the helper, restart the agent, then
`limactl stop` and `start` — with a watcher on the second device throughout.

Assertions: the `*_fresh_attempt` set, `same_storage_generation`,
`profile_marker_survived_losses`, `vm_stop_start_same_disk`,
`screen_withdrawn_during_loss`, `screen_returned_after_sweep_and_policy` (the
screen returns strictly after the helper handshake, the boot sweep and policy
readiness — never before), `old_session_authority_rejected`.
Evidence: `withdraw_ms`, `return_ms`.

### `mac.reconfiguration` — Reconfiguration

Grow, reset through its crash phase, reimage, detachment receipt, stale CAS, and
abort after a dead node.

Assertions: the Linux set, plus `loop_device_residue_absent`,
`ext4_mount_residue_absent`, `lima_guest_residue_absent`. Evidence carries the
cap ceiling facts: `vm_disk_bytes`, `requested_disk_bytes`, and the refusal above
the ceiling.

### `mac.storage_provenance` — Storage provenance

Cold backup, keep-old restore, clone and custody fork, export to the host
operator-mount root, import (tainted), attest, cap pressure, real ENOSPC.

Assertions: the Linux set, plus `source_node_copy_only` (no cross-node move),
`guest_native_backup_bytes` and `managed_root_owned`. Record two facts
separately and do not conflate them: the **backup bytes** live in the guest's
native filesystem and never traverse virtiofs, while the **custody export** is
deliberately written to the host operator-mount root.

### `mac.guest_authority` — Guest authority

From inside the Computer: `/self`, root submission and provenance, self-scoped
listing, the forbidden route, the 20-inflight boundary, and the revocation race.
Run it twice: once gateway-primary, once with the gateway bind forced to fail so
`DialHostBridge` is selected.

Assertions: the Linux set, plus `gateway_primary_path_used`,
`forced_fallback_dial_host_bridge`, and `never_lan` — no request egressed through
a physical interface. Discovery failure itself must fail start and must not
select the fallback.

### `mac.removal` — Removal

Remove the custody-tainted Computer and require `removed_reduced`; remove the
clean one and require `removed_verified`. Then, and only then:

```sh
sudo launchctl bootout system/dev.wefty.agent
pgrep -fl wefty-agent   # must print nothing
```

and open **one** read-only `VerifyNamespaceReadOnly` helper session for the
independent inventory. This is the attended procedure #403 says the transport
runbook lacks; it exists here because the inventory is the whole point of the
row. Re-install the LaunchDaemon afterwards if the session continues.

Assertions: `verified_absence_outcome_live`, `reduced_custody_outcome_live`,
`reduced_bound_to_tainted_computer`, `independent_helper_inventory_restored`, the
disk, loop, mount, container, task, log and control classes each restored to
baseline, `publication_withdrawn`, `operator_bind_source_untouched`,
`shared_image_cache_untouched`.

### `mac.reference_image_narrowness` — §11 item 4

Import each arm64 child from its own digest-selected Computer OCI tar through
`wefty node load-image`; show the three artifacts carry distinct repositories,
digests and tar names while sharing one candidate commit; then reimage a Computer
and show the binding and storage identity unchanged.

Assertions: `reference_image_is_optional` (an ordinary `kind=oci` service on a
non-reference image still runs), `no_generic_oci_base_claim` (no other image
resolves against the reference repository), `reimage_keeps_service_identity`,
`reimage_creates_no_run` (no `WEFTY_RUN_TOKEN` is minted or injected and no Run
row appears), `distinct_artifacts_one_commit`.

## The destination sentence

`destination` is not a row. It is the spec §10 sentence, recomputed from the rows
by the consumer, with one clause each:

| Clause | Proven by |
| --- | --- |
| `computer_on_mac_node` | `mac.create_boot` |
| `watched_and_controlled_from_second_device` | `mac.remote_takeover` |
| `survives_runtime_and_agent_restart_state_intact` | `mac.restart_survival` |
| `screen_withdrawn_on_authority_loss` | `mac.remote_takeover`, `mac.restart_survival` |
| `unauthorized_peer_denied` | `mac.remote_takeover` |
| `removal_proves_managed_residue_absent` | `mac.removal` |

`destination.asserted` is true only when every clause is attested, every
contributing row is PASS, and no `dev.plain_fabric_identity` deviation is
recorded. The consumer recomputes it and rejects a receipt whose stored verdict
disagrees.

`destination.attestation` says how the sentence was witnessed as a whole, and is
required to be exactly `"human"` or `"scripted"` whenever `asserted` is true. It
is the top-level companion to the per-row `evidence["attestation"]` above: a row
records how *that* row's observation was made, while this records how the
destination itself was witnessed. A blocked or red session leaves it empty.

## Receipt

Store the artifact outside Git. It is strict JSON, decoded with unknown fields
disallowed, and it is *also* the matrix fragment — there is no second mapping
step. Required: `version: 1`, one `session_id` repeated by every row, `commit`
equal to the candidate, `host` (macOS, `limactl`, containerd and runc versions,
`host_memory_bytes`, `vm_memory_bytes`, `vm_cpus`, `vm_disk_bytes`, and
`lima_instances: 1`), `image` (variant, reference, index and platform digests,
archive basename), `fabric_identities` covering the administrator, viewer,
second-device and unauthorized roles with distinct device IDs,
`authority_generations`, `resource_caps`, the Computer, Job, attempt and Storage
IDs, `rendering` (`gpu: false`, the renderer, `/dev/dri` absent),
`timings`, `deviations`, `residue_inventories`, `residue_assertions`,
`destination` (`asserted`, the six `assertions`, and `attestation` —
`"human"` or `"scripted"` whenever `asserted` is true),
`attended_row_counts` and the ten `rows`.

The Fabric identities, image digests and resource caps are setup facts: the
consumer requires them however blocked the session was, because they are known
before any Computer boots. `authority_generations` and the Computer, Job,
attempt and Storage ID lists are the opposite — only a booted Computer produces
them — so the consumer requires those only once some row is PASS. A session
blocked before any Computer boots records none of them and is still a valid
fragment.

It must never carry take-over capabilities, Computer bearer values, framebuffer
bytes, keystrokes, tailnet auth keys, credentials or tenant content. The consumer
scans the raw bytes for a redaction denylist and rejects the artifact outright if
it hits.

Validate and emit the fragment with:

```sh
WEFTY_MAC_COMPUTER_ACCEPTANCE_ARTIFACT=/absolute/path/to/redacted-receipt.json \
WEFTY_MAC_COMPUTER_MATRIX_OUT=/absolute/path/to/mac-computer-matrix.json \
  go test -count=1 -run AttendedMacComputerFragment ./serviceacceptance
```

Unlike a destination gate, the producer does not require PASS: a red or blocked
attended session must still produce an honest, typed fragment.

## The merged Computer acceptance matrix (#196)

`scripts/assemble-computer-acceptance-matrix.sh` merges the Linux lane's
version-5 `linux-computer-matrix.json` — copied verbatim, nine rows, no
re-derivation — with this fragment's ten Mac rows into one versioned
`computer-acceptance-matrix.json`, and
`scripts/check-computer-acceptance-matrix.sh` is the fail-closed gate:

```sh
scripts/assemble-computer-acceptance-matrix.sh /absolute/path/to/computer-acceptance-matrix.json \
  "$(git rev-parse HEAD)" published-artifact /path/to/linux-evidence \
  /absolute/path/to/mac-computer-matrix.json owner-hardware
scripts/check-computer-acceptance-matrix.sh /absolute/path/to/computer-acceptance-matrix.json \
  "$(git rev-parse HEAD)" published-artifact owner-hardware
```

**How to read the result.** A typed `NOT-RUN` is an honest "not proven yet" and
passes the gate; a `FAIL` is a proof that ran and came back red, so the gate
exits non-zero and names the row. `complete` is true only when every `mac.*` row
is PASS, and a complete Mac half without `destination.asserted` is itself a
violation — as is a `destination.asserted` sitting on top of a plain-Fabric
deviation. When the second-device and no-grant identities are unavailable, the
honest result is those rows typed `NOT-RUN` with reason
`second_device_unavailable` and the gate reporting `matrix incomplete`.

`realtiming-result` in both realtiming workflows assembles the same matrix with
`none` for the Mac fragment, so every `mac.*` row is a typed `NOT-RUN` owned by
**#128** — carrying, in its `gaps`, the missing owner-hardware prerequisites
(the booted-Computer evidence for the eight rows that need a Computer, and the
second-device setup for the takeover and restart rows) — and the gate prints
`matrix incomplete: 10 Mac rows not run` and exits zero. A GitHub-hosted
runner that claims attended Mac evidence fails the gate, as does a fragment bound
to another candidate commit. A green CI therefore never means a finished matrix.
The scheduled lane's `mutation_row` dispatch passes that row as the gate's fifth
argument; the gate then requires exactly that Linux row to be `FAIL` and no
other. Like the artifact itself, the fragment and the assembled matrix stay
outside Git.
