# v0.1 dogfood acceptance

This is the manual acceptance lane for the buildable part of issue #30. It
uses real tsnet identities, one macOS agent, one Linux agent, and the real
`claude` and `codex` CLIs. Do not run it in CI. Run the full sequence once
pinned to the Mac and once pinned to Linux; tag `v0.1` only after both runs
pass.

The workflow is a serial lineage so one node agent is sufficient per machine:
the root run plans and dispatches the implementation child, the implementation
child commits and dispatches its review child, and L3 holds each parent open
until its descendants settle.

## Prerequisites

- The same accepted wefty commit is checked out on the control-plane host and
  at the paths used below on the Mac and Linux nodes.
- Node.js 22 or newer, npm, Git, `jq`, `claude`, and `codex` are on both agent
  machines. Both CLIs are already authenticated for non-interactive use.
- Four reusable tsnet auth keys are available:
  `TS_AUTHKEY_CONTROL`, `TS_AUTHKEY_CLIENT` (tagged
  `tag:wefty-client`), `TS_AUTHKEY_AGENT_MAC`, and
  `TS_AUTHKEY_AGENT_LINUX` (both tagged `tag:wefty-agent`).
- Tailnet ACLs allow the client and agent identities to reach
  `wefty://control-plane` and `wefty://run-ledger` on their internal port 80.
- The target checkouts are clean and the two acceptance branch names below do
  not already exist.

Set these values in every relevant shell, changing only the two checkout paths
to match the real machines:

```sh
export WEFTY_CONTROL_ROOT=/srv/wefty
export WEFTY_MAC_ROOT=/Users/derekxwang/Development/wefty
export WEFTY_LINUX_ROOT=/srv/wefty
export WEFTY_STATE_ROOT=/var/tmp/wefty-v0.1
export TS_CONTROL_URL="${TS_CONTROL_URL:-}"
```

On each of the three hosts, install/build from its local checkout. On the two
agent machines the `npm test` command is the fake-agent plain-fabric contract
smoke; it does not call an LLM.

```sh
cd "$WEFTY_CONTROL_ROOT"
mkdir -p .bin "$WEFTY_STATE_ROOT"
go build -o .bin/wefty-l1 ./cmd/wefty-l1
go build -o .bin/wefty-l3 ./cmd/wefty-l3
go build -o .bin/wefty ./cmd/wefty

cd workflows/dogfood
npm ci
npm run lint
npm run typecheck
npm test
```

Repeat the workflow-package commands in `$WEFTY_MAC_ROOT/workflows/dogfood`
and `$WEFTY_LINUX_ROOT/workflows/dogfood`. Build `wefty-agent` on each agent:

```sh
cd "$WEFTY_MAC_ROOT" # use WEFTY_LINUX_ROOT on Linux
mkdir -p .bin "$WEFTY_STATE_ROOT"
go build -o .bin/wefty-agent ./cmd/wefty-agent
```

## Start the control plane

On the control-plane host, terminal 1:

```sh
cd "$WEFTY_CONTROL_ROOT"
./.bin/wefty-l1 \
  --fabric=tsnet \
  --listen=wefty://control-plane \
  --fabric-name=wefty://control-plane \
  --state-dir="$WEFTY_STATE_ROOT/l1-tsnet" \
  --auth-key="$TS_AUTHKEY_CONTROL" \
  --control-url="$TS_CONTROL_URL" \
  --db="$WEFTY_STATE_ROOT/l1.sqlite" \
  --node-tags=dogfood-mac=mac,arm64,wefty:node:dogfood-mac \
  --node-tags=dogfood-linux=linux,amd64,wefty:node:dogfood-linux
```

On the same host, terminal 2:

```sh
cd "$WEFTY_CONTROL_ROOT"
./.bin/wefty-l3 \
  --fabric=tsnet \
  --listen=wefty://run-ledger \
  --control-plane=wefty://control-plane \
  --fabric-name=wefty://run-ledger \
  --state-dir="$WEFTY_STATE_ROOT/l3-tsnet" \
  --auth-key="$TS_AUTHKEY_CLIENT" \
  --control-url="$TS_CONTROL_URL" \
  --db="$WEFTY_STATE_ROOT/l3.sqlite" \
  --reconcile-interval=1s
```

```sh
cd "$WEFTY_CONTROL_ROOT"
./.bin/wefty \
  --fabric=tsnet \
```

`dogfood-linux` with a Linux/amd64 OS/architecture. Both must be `alive` and
show their reserved `wefty:node:*` tag.

## Submit from Claude Code

Run the following commands from the shell tool inside the Claude Code session
driving acceptance. The `wefty submit` command sends `POST /v1/runs` through
the Fabric seam; the stored inline script is the small build output, while the
runtime loads exactly `@ai-hero/sandcastle@0.12.0` from the pinned workflow
package on the selected node.

Create the Mac input:

```sh
jq -n \
  --arg task "Add a small, reviewable improvement selected for the v0.1 dogfood run; run focused tests and commit it." \
  --arg repo "$WEFTY_MAC_ROOT" \
  --arg package "$WEFTY_MAC_ROOT/workflows/dogfood" \
  '{task:$task,repo_path:$repo,workflow_package_path:$package,base_branch:"main",branch:"acceptance/v0.1-mac-20260809"}' \
  > /tmp/wefty-v0.1-mac-params.json
```

Submit it pinned to the Mac and capture the root run ID:

```bash
cd "$WEFTY_CONTROL_ROOT"
set -o pipefail
MAC_RUN_ID=$(
  ./.bin/wefty \
    --fabric=tsnet \
    --fabric-name=wefty://node/dogfood-operator \
    --state-dir="$WEFTY_STATE_ROOT/operator-tsnet" \
    --auth-key="$TS_AUTHKEY_CLIENT" \
    --control-url="$TS_CONTROL_URL" \
    --json \
    submit \
    --script=workflows/dogfood/dist/dogfood-workflow.mjs \
    --interpreter=node \
    --params-file=/tmp/wefty-v0.1-mac-params.json \
    --tag=wefty:node:dogfood-mac \
    --required-envelope \
    --max-runtime=7200 \
    --idempotency-key=v0.1-dogfood-mac-20260809 \
  | tee /tmp/wefty-v0.1-mac-submit.json \
  | jq -er '.run_id | select(type == "string" and length > 0)'
)
test -n "$MAC_RUN_ID"
printf '%s\n' "$MAC_RUN_ID"
```

Follow the root log, wait for terminal settlement, and inspect all three runs:

```sh
./.bin/wefty \
  --fabric=tsnet \
  --fabric-name=wefty://node/dogfood-operator \
  --state-dir="$WEFTY_STATE_ROOT/operator-tsnet" \
  --auth-key="$TS_AUTHKEY_CLIENT" \
  --control-url="$TS_CONTROL_URL" \
  logs "$MAC_RUN_ID" --follow

./.bin/wefty \
  --fabric=tsnet \
  --fabric-name=wefty://node/dogfood-operator \
  --state-dir="$WEFTY_STATE_ROOT/operator-tsnet" \
  --auth-key="$TS_AUTHKEY_CLIENT" \
  --control-url="$TS_CONTROL_URL" \
  --json inspect "$MAC_RUN_ID" \
  | tee /tmp/wefty-v0.1-mac-inspect.json
```

Create and submit the Linux input with the same guarded pipeline:

```bash

  --arg repo "$WEFTY_LINUX_ROOT" \

  '{task:$task,repo_path:$repo,workflow_package_path:$package,base_branch:"main",branch:"acceptance/v0.1-linux-20260809"}' \
  > /tmp/wefty-v0.1-linux-params.json

set -o pipefail
LINUX_RUN_ID=$(
  ./.bin/wefty \
    --fabric=tsnet \
    --fabric-name=wefty://node/dogfood-operator \
    --state-dir="$WEFTY_STATE_ROOT/operator-tsnet" \
    --auth-key="$TS_AUTHKEY_CLIENT" \
    --control-url="$TS_CONTROL_URL" \
    --json \
    submit \
    --script=workflows/dogfood/dist/dogfood-workflow.mjs \
    --interpreter=node \
    --params-file=/tmp/wefty-v0.1-linux-params.json \
```

Follow logs and run `--json inspect "$LINUX_RUN_ID"` exactly as above, writing
the inspection to `/tmp/wefty-v0.1-linux-inspect.json`.

To print every parent and child log after either run settles:

```sh
jq -r '.runs[].run_id' /tmp/wefty-v0.1-mac-inspect.json | while read -r run_id; do
  printf '\n===== %s =====\n' "$run_id"
  ./.bin/wefty \
    --fabric=tsnet \
    --fabric-name=wefty://node/dogfood-operator \
    --state-dir="$WEFTY_STATE_ROOT/operator-tsnet" \
    --auth-key="$TS_AUTHKEY_CLIENT" \
    --control-url="$TS_CONTROL_URL" \
    logs "$run_id"
done
```

## Expected records and pass criteria

For each root inspection:

- `.run.status` is `succeeded` only after both descendants settle.
- `.runs` has exactly three records in lineage order: root `plan`, child
  `implement`, grandchild `review`.
- Every record has one accepted envelope with a non-empty, server-bound
  `attempt_id`; envelope statuses are `succeeded`.
- Every record has one gate with a non-empty `attempt_id`; gate outcomes are
  `pass` (`plan-produced`, `implementation-committed`, `cross-review`).
- Every Mac inspection record has `node_id` equal to `dogfood-mac`, and every
  Linux inspection record has `node_id` equal to `dogfood-linux`. This is the
  run-record evidence that each root and descendant executed on the intended
  agent node.
- The implementation envelope contains at least one `git:<sha>` artifact and
  the named acceptance branch contains that commit. Review corrections, if
  any, appear as `review-fix` artifacts on the same branch.
- Root and child logs show the plan, Codex implementation, Claude review, and
  child run IDs. Logs do not contain the run token; any accidental occurrence
  is `[REDACTED]`.
- `wefty nodes list` still shows both nodes alive after the runs; placement is
  proven by each run record's `node_id`, not by fleet registration metadata.

Use this mechanical check for each inspection file:

```bash
jq -e --arg node dogfood-mac '
  .run.status == "succeeded" and
  (.runs | length) == 3 and
  ([.runs[].envelopes[0].step_id] == ["plan","implement","review"]) and
  ([.runs[].envelopes[0].status] | all(. == "succeeded")) and
  ([.runs[].gates[0].outcome] | all(. == "pass")) and
  ([.runs[].node_id] | all(. == $node)) and
  ([.runs[].envelopes[0].attempt_id] | all(length > 0)) and
  ([.runs[].gates[0].attempt_id] | all(length > 0))
' /tmp/wefty-v0.1-mac-inspect.json
```

Run it again with `--arg node dogfood-linux` against
`/tmp/wefty-v0.1-linux-inspect.json`. Record both root
run IDs, the accepted commit, node OS/architecture, inspection JSON, and any
review-fix SHAs in issue #30. A failed/errored gate, missing envelope, failed
descendant, absent logs, wrong node, or real CLI invocation failure fails
acceptance and must not be papered over by tagging.

## Tag only after both human runs pass

This command is intentionally not part of the automated build. After the Mac
and Linux evidence is attached to issue #30 and both runs meet every criterion:

```sh
cd "$WEFTY_CONTROL_ROOT"
git tag -a v0.1 -m "wefty v0.1: dogfood workflow accepted on macOS and Linux"
git push origin v0.1
```
