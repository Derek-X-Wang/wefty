# warpweft — Deep Research Synthesis Report

Personal compute fabric: **L1** cluster of owned Macs + cloud VMs (Tailscale networking, native + OCI runtimes, deliberately dumb scheduler); **L2** connector system making external API-launchable compute appear as schedulable capacity; **L3** optional software-factory-inspired app layer for workflow planning/scheduling/observability.

Research date for all briefs: 2026-08-06. Facts below are preserved verbatim from the underlying briefs; conflicts are flagged inline and collected in §7.

---

## 1. Key Facts Per Area

### 1.1 sandcastle (mattpocock/sandcastle) — agent-orchestration prior art

- TS library + CLI orchestrating AI coding agents in sandboxes: one `sandcastle.run()` handles sandbox lifecycle, git worktree/branch management, prompt assembly, agent loop, merge-back. npm `@ai-hero/sandcastle`, MIT.
- **Maturity:** 7,235 stars, 734 forks, ~9 contributors, 126 open issues. Repo created 2026-03-17; latest v0.12.0 published 2026-06-29 — also the **last push to main (~5.5 weeks quiet)**. Pre-1.0, API churning (0.4.0 replaced worktree config with `branchStrategy`; 0.5.0 restructured hooks). Whether the gap is abandonment or v1 rework: unverified.
- Two provider classes: **bind-mount** (Docker/Podman — worktree mounted at `/home/agent/workspace`, process-level isolation only, network NOT isolated by default) and **isolated** (Vercel Firecracker microVMs, Daytona — `copyIn`/`copyFileOut` sync). Plus `noSandbox()`.
- Custom provider interface is small and clean: `exec` / `copyFileIn` / `copyFileOut` / `close` / `worktreePath` (`createBindMountSandboxProvider` / `createIsolatedSandboxProvider`) — directly reusable seam for pointing at your own fleet.
- Branch strategies: `head`, `merge-to-head`, `branch`. Worktree locking (ADR 0007) + reuse (ADR 0003).
- Agent providers: `claudeCode`, `codex`, `pi`, `cursor`, `opencode`, `copilot`; session capture/resume for Claude Code/Codex/Pi; Claude Code session **fork** (ADR 0018).
- Patterns worth stealing regardless of adoption: completion-signal + idle (600s) / completion (60s) timeouts for hang detection; `Output.object({tag, schema: zod, maxRetries})` structured-output-with-retry; sandbox-side `` !`cmd` `` prompt expansion (ADR 0020); UID/GID build-arg alignment (ADR 0005/0014); self-hosting agent CI workflows (`.github/workflows/agent-*.yml`).
- Maintainer explicitly rejects (`.out-of-scope/`): bundled workflow templates, multi-repo sandboxes, provider retry — warpweft would own those layers.
- Runtime deps tiny (`@clack/prompts`); peer deps `@vercel/sandbox >=1.0.0`, `@daytona/sdk ^0.164.0` (optional; note Daytona SDK is at 0.203.0 — version lag). Daytona provider is in source but was not in the README provider table.

### 1.2 Software factory trend (disler/SSSF + landscape) — L3 design input

- **SSSF** (https://github.com/disler/super-simple-software-factory, MIT, ~432 stars/~102 forks): "Agent proposes, code disposes." Control plane moved from prompts into deterministic Python.
  - **ADW** (AI Developer Workflow) = a plain Python script that IS the workflow definition and scheduler (`uv run adws/adw_*.py "<prompt>" [--config] [--adw-id]`).
  - **Phases** (Engineer / Agent / Code) as atomic units; `run.finish(accepted=bool)`.
  - **Envelopes** — typed JSON agent outputs (`EnvelopeBase`: status, summary, artifacts, notes_for_next_agent; extensions like `BuildOutput.changed_files`).
  - **Gates** — post-hoc verification of claims (`artifacts_exist`, `files_non_empty`, `json_parses`, `diff_matches_claims`, `tests_pass`); failed gates **re-prompt the same warm agent session** rather than cold-restarting — a cheap retry semantic worth copying as a scheduling primitive.
  - **Handoffs** via files (`context_handoff/`, `envelope.json`), never conversation history. `--adw-id` = durable run/session identity for resumption and workflow chaining.
  - Single-YAML agent roster (`sssf.config.yaml`): per-agent model (mixed providers), thinking level, prompts, and a `writes:` path allowlist — effectively a resource+permission spec per node.
  - Observability: "agents write to SQLite, readers poll SQLite" — WAL DB, 7 tables (`sessions`, `phases`, `events`, `envelopes`, `gate_results`, `agent_sessions`, `processes`), span nesting via `parent_id`, live tail by `rowid` polling, no WebSockets; raw `raw_output.jsonl` stays authoritative. Vue/Vite/Bun trace visualizer on port 4600.
  - 12 starter ADWs (`adw_prompt` … `adw_simple_sdlc`). Harness: **Pi** (badlogic/pi-mono, `@mariozechner/pi-coding-agent`); Claude Code "stubbed."
  - **Deliberately single-machine/sequential — no parallelism, queueing, or cluster scheduling.** That gap is exactly warpweft L3's job.
- **Landscape:**
  - Geoffrey Huntley's **Ralph Wiggum** loop (https://ghuntley.com/ralph/, coined May–Jul 2025; `while :; do cat PROMPT.md | agent; done`) became an official Anthropic Claude Code plugin (Dec 2025).
  - **Gas Town** (Steve Yegge, Jan 1 2026): Go orchestrator, 20–30 parallel Claude Code agents in tmux; **Beads** = git-backed JSONL issue tracker as atomic work units; 7 agent roles; "Nondeterministic Idempotence" — durable workflow execution for LLMs.
  - **Factory.ai "Factory 2.0"** (June 15, 2026): Droids + Skills, Missions (multi-agent decomposition into parallel tracks), Droid Computers (remote persistent execution), Model Router. Deployed at NVIDIA, Adobe, Palo Alto Networks, Adyen. Pricing not in the post (app-layer brief cites tiers ~$20/$100/$200/mo — treat the $ figures as the softer source).
  - **OpenAI Symphony** (open-source spec): PM board as a control plane for coding agents — every open task gets an agent.
  - Mid-2026 practitioner consensus: **"workflows beat free-form agents"** (Aviator, Tembo/Augment Code posts) — validates the deterministic-graph stance.
  - OSS orchestrators: Composio agent-orchestrator, Conductor (Melty Labs, macOS), vibe-kanban (Bloop), claude_code_agent_farm, Emdash/Baton/Dorothy; curated list https://github.com/andyrewlee/awesome-agent-orchestrators (~150 tools).

### 1.3 Ona (ex-Gitpod)

- **OpenAI announced acquisition June 11, 2026**; ~79-person team joins Codex group; deal expected to close Q3 2026 — **closing not verified as of 2026-08-06**. Go SDK already ships `RunCodex` + `CODEX_OPEN_AI_MODEL_GPT_5_6_SOL` enums.
- API: Connect RPC (POST + protobuf-JSON), base `https://app.ona.com/api`, route `/api/{service}.{version}.{ServiceName}/{MethodName}`. Bearer PAT/service-account token; `ONA_API_KEY`/`GITPOD_API_KEY`.
- SDKs: Go (`github.com/gitpod-io/gitpod-sdk-go`, active, pushed 2026-08-03), Python (`gitpod-sdk`), TS (`@gitpod/sdk`). **No Rust.**
- Lifecycle: create/start/stop/delete environments; supervisor-backed exec/file/git ops; Codex agent sessions with `MessageStream`. Prebuilds, not arbitrary snapshots. Programmatic port-expose: **unverified**.
- Pricing: Core from $20/mo, OCU credits (1 OCU ≈ 1 hr of 4 vCPU/16 GB); **API/SDK access is Enterprise-only** (self-serve API does not exist). Rate limits unpublished.
- **Verdict: do not build on as neutral capacity** — Enterprise-gated + being absorbed into Codex Cloud within ~12 months.

### 1.4 Daytona

- Independent, $24M Series A (Feb 2026, FirstMark). `daytonaio/daytona` **~72,000 stars**, pushed 2026-07-24. License reported AGPL-3.0 for the open stack — **GitHub API returns no license field; unverified**.
- Three REST APIs with OpenAPI specs (Platform, Toolbox, Analytics); base `https://app.daytona.io/api`; self-serve API keys.
- SDKs in lockstep at **v0.203.0 (2026-07-31)**: TS (`@daytona/sdk`), Python (`daytona`), Go (`github.com/daytona/clients/sdk-go`), Ruby, Java. **No official Rust** — OpenAPI codegen path.
- Lifecycle: create/start/stop/delete/archive; container or VM sandboxes; warm pools, **sub-90ms claimed boot**; snapshots dual-purpose — image templates AND point-in-time state (cold for containers; **hot VM snapshots incl. memory via `_experimental_create_snapshot()`** — still experimental). Snapshots auto-deactivate after 2 weeks unused.
- Exec: `process.exec()`, stateless `code_run()`, stateful `codeInterpreter.runCode()`, **sessions** with `runAsync: true` + interactive stdin. WebSocket log streaming; HTTP `?follow=true`.
- Ports: any 1–65535 via preview URLs (`https://{port}-{sandboxId}.{proxyDomain}` + `x-daytona-preview-token`, resets on restart) or **signed URLs** (TTL 1–86,400s, default 60s, revocable, no headers). WebSocket passthrough on preview URLs: undocumented/unverified. Also SSH, VNC, web terminal, multi-region.
- Pricing: per-second — vCPU $0.0504/hr, memory $0.0162/GiB-hr, storage $0.000108/GiB-hr; Windows $0.0858/vCPU-hr; GPUs H200 $4.54/hr → RTX 4090 $0.99/hr. **$200 free credits + 5 GB free storage.** Tiers T1 (10 vCPU/20 GiB/30 GiB concurrent) → T4 ($2,000/30d: 500/1,000/5,000). Rate limits 10k–50k API req/min, 300–600 sandbox creations/min, `DaytonaRateLimitError` + headers.
- **Verdict: connector-ready today — the strongest external-capacity fit.**

### 1.5 Other sandbox providers (E2B, Modal, Fly Machines, Cloudflare, Vercel)

- **E2B:** Firecracker microVMs; open core + heavy self-host (Nomad+Firecracker, Terraform on GCP/AWS). `Sandbox.create()`, commands/filesystem APIs, `getHost(port)` public URL per port. **Pause/resume is GA and preserves memory** (~4 s/GiB pause, ~1 s resume, paused kept indefinitely); `lifecycle: {onTimeout: 'pause'}`. Max continuous runtime 1 h Hobby / 24 h Pro (pause resets clock). SDKs: TS/Py only; unofficial Rust crate `e2b-sdk` (treat as unmaintained). Pricing: Hobby free ($100 credits); Pro $150/mo + ~$0.000014/vCPU-s; billed from boot. Cold start ~150 ms claimed, 300–800 ms practical.
- **Modal:** gVisor containers; `Sandbox.create()` with image/volumes/secrets/GPUs, streamed `exec`, tunnels, readiness probes; best reconciliation ergonomics (`from_id`, `from_name`, tags, `list()`). FS snapshots GA (30-day TTL default); **memory snapshots alpha** (7-day TTL, terminates sandbox on capture, no GPU). SDKs: Python full; **JS/TS and Go official (beta, sandbox-focused)**; no Rust; **no public REST — gRPC via SDK only**. Pricing: CPU $0.00003942/core-s (~$0.142/core-hr), memory ~$0.00000667/GiB-s (derived, may be stale); Starter free $30/mo credit; Team $250/mo, 1,000 containers. Cold start sub-second claimed, ~0.5–2 s realistic.
- **Fly Machines:** Firecracker VMs behind **plain REST** (`api.machines.dev`, OpenAPI published): create (`skip_launch`), start/stop/**suspend**/signal/cordon, `GET .../wait?state=`, metadata KV, **leases** (`fly-machine-lease-nonce`) for exclusive-writer semantics. `exec` is weak: 60 s timeout, buffered, no background processes — **BYO in-VM agent**. Suspend is best-effort/non-durable (host migration invalidates snapshot). Official Go SDK (`superfly/fly-go`). Pricing: shared-cpu-1x/256MB ≈ $0.0028/hr; **stopped = rootfs storage only at $0.15/GB-mo** (best idle economics); no platform fee. Cold start ~300 ms–1 s stopped→started.
- **Cloudflare Sandboxes/Containers:** `@cloudflare/sandbox` (~1.1k stars, GA April 2026) — but the SDK **runs inside a Worker/Durable Object; an external orchestrator cannot call sandboxes directly** (must deploy a Worker shim). TS only. No memory snapshots. Max instance 4 vCPU/12 GiB. Per-10ms billing on Workers Paid ($5/mo). "100x faster ms-level starts" marketing unverified independently.
- **Vercel Sandbox:** Firecracker (Amazon Linux 2023), **iad1 only**. `runCommand` streaming, `domain(port)` (≤15 ports), persistent sandboxes (auto-save on stop, now default), explicit snapshots (30-day expiry), drives (beta), custom OCI images (beta), sudo (Docker-in-sandbox possible). SDKs TS + Python + CLI; no Go/Rust; raw REST undocumented. **Billing: Active CPU $0.128/hr with I/O wait not billed** — materially cheapest for idle-heavy agent loops; memory $0.0212/GB-hr; creations $0.60/1M. Hobby free tier: 5 CPU-hr, 420 GB-hr, 5k creations/mo, 10 concurrent; Pro/Ent 10,000 concurrent. Cold start "milliseconds" marketing; no published p50/p99.
- **Brief's ranking as orchestrator backends:** (1) Fly Machines, (2) E2B, (3) Modal, (4) Vercel, (5) Cloudflare. Note this ranking excludes Daytona (covered separately), which the ona-daytona brief rates as the top overall connector fit.

### 1.6 Go ecosystem

Full detail in §2 table. Headlines: Docker Go SDK moved to `github.com/moby/moby/client` at v29 (docker/docker ends at v28.x — security fixes only land in moby modules); containerd v2 client is the most complete high-level client anywhere; `google/go-containerregistry` enables daemonless image pull/push; **tsnet is Go's asymmetric advantage** (embedded tailnet node + `WhoIs` identity, no other language has it first-class); Apple `container` is the one hostile island (Swift/XPC only — CLI-wrap or cgo Swift-bridge via crunchloop/devcontainer's `libACBridge.dylib` pattern); Lima importable as `github.com/lima-vm/lima/v2` (Colima/Rancher Desktop/Finch consume it) but library API is internal-ish; kardianos/service for service install; no standard-library-grade process supervisor for non-container child processes (assemble suture + oklog/run + creack/pty).

### 1.7 Rust ecosystem

Full detail in §2 table. Headlines: **bollard** is the strongest crate (moby API 1.52, Podman first-class, SSH tunnels); **youki/libcontainer** lets the Linux agent *be* the OCI runtime in-process (no Go equivalent — runc's libcontainer is famously awkward to embed); **wasmtime** embedding is best-in-class (v47.0.1, monthly releases, 24-month LTS channel); containerd Rust client is raw gRPC (thinner than Go); **Tailscale is Rust's biggest single gap** — tailscale-rs is experimental/DERP-only (`TS_RS_EXPERIMENT=this_is_unstable_software`, no NAT traversal, crypto unaudited); pragmatic path is tailscaled LocalAPI (unix socket, HTTP+JSON) or CLI `--json`. WireGuard-in-Rust is fragmented (boringtun stewardship unreliable; NepTUN / firezone forks; defguard_wireguard_rs for kernel control-plane). `service-manager` crate (v0.11.0, 475k downloads) covers cross-platform service install.

### 1.8 macOS runtime (Apple silicon, background daemon)

See §5. Headline: **Lima v2.2.0 (2026-07-21) is the only actively-maintained option with explicit, first-party LaunchDaemon/headless support** (issue #4983/PR #4984 — VMs survive reboot with no login). Apple `container` v1.2.0 (2026-07-29) is architecturally per-user LaunchAgent + login Keychain + XPC — no documented headless mode, open wedge bugs (#621, #1916). Colima's brew-services LaunchAgent is flaky and login-scoped. OrbStack: excellent CLI but proprietary, free tier personal-only ($8/mo Pro for any work use). Docker Desktop: excluded (engine stops on logout, docker/for-mac#3567, #6504).

### 1.9 Unified-compute prior art (connector-layer design input)

See §3. Headline lessons: (1) honest capacity model — Nomad remote task drivers (issue #10549) are the definitive failure record for mapping elastic API capacity onto machine-shaped resource stanzas (feature shipped 1.1, deprecated, fully removed ~1.10/GH-24909); (2) out-of-process contracts beat compiled-in interfaces (Virtual Kubelet's stated regret; interLink, Cluster API, kubernetes-sigs/agent-sandbox all converge there); (3) the backend-vs-fleet two-layer split recurs (dstack, CAPI, SkyPilot); (4) sandbox lifecycle verbs (pause/resume/snapshot/warm-pool-claim) must be first-class; (5) cost/availability metadata per provider (SkyPilot's catalog+optimizer) is the main payoff of heterogeneity. **No shipped OSS project federates local machines + cloud VMs + sandbox APIs under one scheduler as of mid-2026 — warpweft's combination appears to be open ground.**

### 1.10 Tailscale as infrastructure

See §6. Headlines: tsnet v1.102.2 (BSD-3, ~252 importers); Tailscale HTTP API + OAuth-client key-minting loop; Funnel limited to TCP ports 443/8443/10000, no custom domains (#11563), undisclosed bandwidth limits; **Tailscale Services GA Feb 19, 2026** (`svc:name` MagicDNS + virtual IPs, 10 services/tailnet incl. Personal, hosts must be tagged); pricing v4 (April 8, 2026): Personal free = 6 users, unlimited user devices, **50 tagged resources, 1,000 ephemeral-resource minutes/month**, 3 ACL groups, non-commercial; headscale v0.28.0 (~42.6k stars, Tailscale employs a maintainer, no Funnel/Serve support); Coder is the strongest commercial embed precedent (embedded DERP inside `coder server`).

**Net shape (both briefs concur):**
- **Go wins if:** embedded mesh networking in-process (tsnet + `WhoIs` authn) is a hard requirement; you want the same libraries the reference tools are built from (moby, containerd, Lima, gVisor, Tailscale are all Go); you want native SDKs for Fly/Modal/Daytona/Ona.
- **Rust wins if:** the design uses tailscaled-via-LocalAPI rather than embedded tsnet, **and** the fabric leans on Wasm workloads (wasmtime/runwasi) or wants the node agent to be the container runtime itself (libcontainer); plus lower RSS/no GC jitter for an always-on agent.
- Neutral either way: gVisor, Apple `container` (both are exec/CLI integrations from any language).

## 3. Connector-Layer (L2) Abstraction Candidates

| Pattern | Source | Trade-offs / verdict for Daytona/E2B/Modal-style connectors |
|---|---|---|
| **Fake node + pod translation** | Virtual Kubelet (~4.5k stars; providers = compiled-in Go `PodLifecycleHandler`), Liqo | Proven commercially (ACI, Fargate, ECI) — scheduler needs zero changes. Fails on: compiled-in provider maintenance burden (stated in VK 1.0 deep-dive), pod-semantics gaps (DaemonSets, hostPath, exec/logs), and **one giant elastic node distorts bin-packing** (Liqo docs call it out). Only viable if the scheduler understands "elastic node." |
| **HTTP plugin contract behind a node facade** | interLink (CERN/interTwin) | **Best split of concerns found.** Control-plane-side shim stays stable; provider plugin = small REST daemon in any language (Slurm, Docker, HTCondor in production). Inherits VK pod-semantics gaps; niche/academic maintenance. Directly reusable shape for warpweft. |
| **Provider interface + catalog + optimizer** | SkyPilot (~10.5k stars; v0.12.0 added Slurm backend; Shopify production multi-cloud) | Right shape for *choosing among* providers (price/availability shopping = the killer feature). Wrong shape for sandbox APIs: `clouds.Cloud` assumes an SSH/exec-able VM the runtime rides on; controller memory caps managed jobs (max 512); single-user CLI DNA. **Steal the catalog idea** (price, cold-start latency, isolation class, GPU availability per provider) even if execution differs. |
| **Backend (credentials) + fleet/pool (capacity) split** | dstack (~2.2k stars, v0.20.17) | **Cleanest user-facing model for mixing owned machines with elastic capacity.** SSH fleets = any Linux host over SSH becomes schedulable, no backend needed; `blocks` subdivides a big box; sandbox provider maps naturally to a `nodes: 0..N` elastic fleet with per-second pricing. Costs: host prep on you (passwordless sudo + Docker/drivers); smaller community. |
| **Declarative provider contract (CRDs + status handshake)** | Cluster API | Best decoupling for third-party provider authors; but heavy (management cluster, many CRDs, slow reconciles) and wrong layer (machines, not jobs). The *contract-not-interface* idea transfers. |
| **Driver plugin proxying to remote API** | Nomad remote task drivers (1.1 → removed) | **Tried and removed — anti-pattern.** Issue #10549: Nomad's cpu/mem stanza vs Lambda's "memory implies CPU" made the resources block meaningless yet still drove wrong bin-packing; config-authority confusion; HashiCorp chose removal over scheduler-aware fixes. Counter-example: Koyeb's custom Firecracker task driver works fine — because the driver's node really is the executing machine. |
| **Sandbox CRD + WarmPool/claim + portable backend proto** | kubernetes-sigs/agent-sandbox (SIG Apps, GA-track through 2026) | Emerging standard for exactly the sandbox lifecycle (create/claim/hibernate/resume; roadmap: 1000+ claims/sec, sub-100ms assignment, "decouple API from runtime via a common proto backend"). Candidate wire contract for warpweft's sandbox side — watch it. |

**Distilled design rules for warpweft L2:**
1. **Honest capacity model**: owned Mac = finite cpu/mem; provider = elastic pool with price / rate-limit / quota / concurrency-tier dimensions (Daytona T1–T4 tiers are a literal example). Never reuse machine-shaped resource stanzas for elastic capacity (Nomad #10549).
2. **Out-of-process connector contract** (HTTP/gRPC/proto), not compiled-in interfaces — matches the "deliberately dumb scheduler" goal: the cluster API stays stable while connectors churn.
3. **Two layers**: connector/backend (auth + provider API client) vs pool/fleet (schedulable capacity with placement attributes).
4. **Lifecycle verbs beyond run**: create / exec / pause / resume / snapshot / warm-claim must be first-class in the contract, with per-provider capability flags (E2B has GA memory pause; Modal's is alpha; Fly suspend is best-effort; Daytona hot snapshots experimental; Cloudflare has none).
5. **Catalog metadata per connector**: $/vCPU-hr, cold-start class, isolation class (microVM/gVisor/container), max lifetime, idle economics, region — this is what makes heterogeneity pay.
6. **Per-provider realities to encode**: Cloudflare needs a Worker shim (or skip it); Modal needs an embedded SDK process (no REST); Fly needs a BYO in-VM exec agent; Vercel/E2B are TS/Py-SDK-gated; Daytona and Fly are the two with clean REST+OpenAPI.

## 4. App-Layer (L3) v1 Shape

Intersection of all surviving products (Porter, Windmill, Temporal UI, Coolify, Dokploy, Retool Workflows, Airplane post-mortem, Devin/Factory):

**v1 feature set (everything else is demonstrably v2+):**
1. **Work definition** — named unit (task/script/session) with typed params/config schema; config-as-code file in repo + UI editor over it (Airplane task, Windmill script, Porter `porter.yaml`, Devin `playbook + structured_output_schema`).
2. **Triggers** — exactly four: manual run (form generated from params schema), cron, webhook, chain (workflow→workflow / parent→child). That quartet is the complete set across Retool/Windmill/Airplane.
3. **Run history** — append-only records: status, timestamps, who/what triggered, params in, result out, per-run logs; explicit retention window (Porter: 7-day logs / 14-day metrics); metering per run (Retool) or per compute-minute (Devin ACU ≈ 15 min active work).
4. **Live logs** — stream to UI during execution, persist after (Coolify: DB-stored + streamed; Windmill: streamed to Postgres).
5. **Capacity/node view** — workers-and-queues page: active workers, group/tags served, queue depth/delay (Windmill Workers page, Temporal task-queue pollers, Porter cluster observability).
6. **Control actions** — cancel/terminate + re-run-with-same-inputs minimum; Temporal's signal/reset/update are v2.
7. **Saved filters/views** over runs (Temporal saved views) — cheap, high leverage.

**How L3 talks to L1/L2 — four proven patterns (plus a fifth):**

| Pattern | Example | Mechanism | Fit for warpweft |
|---|---|---|---|
| Shared-DB pull queue | Windmill | Workers poll Postgres every 50ms, atomic row-lock claim (`FOR UPDATE SKIP LOCKED`-style), **tags route jobs to worker groups** (`WORKER_GROUP`/`WORKER_TAGS`, hot-reloadable); no broker; ~26M jobs/mo/worker | **Best match** — same trust domain over the tailnet; tags = the "dumb scheduler" routing primitive |
| Agent reverse tunnel | Rancher (`cattle-cluster-agent`) | Agent dials out, WebSocket + TCP tunnel back; no inbound firewall rules ever; cluster lost if WS drops | Tailscale mesh mostly obviates this for L1; the *pattern* matters for L2 connectors behind NAT |
| Push over SSH / Docker API | Coolify (SSH + ControlMaster), Dokploy (dockerode + Swarm-even-on-single-node) | Control plane holds creds, runs commands remotely; Redis/Horizon queue serializes deploys | Zero-agent-install option for small owned fleets; Dokploy lesson: **delegate clustering to the orchestrator, keep the app layer thin** |
| Wrap the orchestrator's API | Porter (Helm releases + in-cluster porter-agent), Temporal UI (visibility queries + control RPCs) | App layer stores desired state, translates to the orchestrator; orchestrator owns reconciliation | **This is warpweft's L3↔L1 contract**: L3 is a thin surface over the cluster API, Temporal-UI-style |
| REST session API | Devin (`POST /v3/organizations/{org}/sessions` with prompt, playbook_id, repos, max_acu_limit, structured_output_schema, tags, create_as_user_id) | Agent VM treated as a metered job | The shape L3 should *expose upward* to AI agents |

**Software-factory ingredients to fold in (from SSSF/Gas Town/Symphony):** phases ≈ tasks; typed envelopes ≈ task outputs; gates ≈ acceptance tests before downstream tasks fire; gate-failure → re-prompt warm session (retry semantic); handoff files ≈ artifact store; adw-id ≈ durable run identity; single-YAML roster (model/effort/write-scope) ≈ per-node resource+permission spec; SQLite/Postgres-as-the-only-data-path with rowid/poll live-tail ≈ observability without WebSockets. Converged UX shape across the 2026 category: **plan (LLM decomposes) → cards/tasks → dispatch to isolated compute → review gate (diff/PR) → merge queue**, human-in-the-loop at plan approval and review.

**Cautionary tales:** Airplane.dev — beloved product, killed March 1, 2024 after Airtable acquihire despite revenue; don't build on closed workflow SaaS. Porter's OSS control plane archived (porter-archive) — SaaS-only now. Bloop (Vibe Kanban) reportedly shut ~April 2026, project community-maintained (single secondary source).

## 5. macOS Runtime Recommendation Candidates and Traps

### Candidates

| Backend | Version | Headless story | Verdict |
|---|---|---|---|
| **Lima** | v2.2.0 (2026-07-21), vz driver default on macOS ≥13.5, virtiofs | **Only option with shipped first-party LaunchDaemon support** (issue #4983/PR #4984): root LaunchDaemon starts instances at boot, no login needed. CVE-2026-53657 fixed; socket_vmnet restricted to admin group | **Primary recommendation** — drive via `limactl` + nerdctl/containerd (or Docker-socket template); agent talks to containerd in-VM (Go client or forwarded socket over tsnet) |
| **Apple `container`** | v1.0.0 (2026-06-09) → v1.2.0 (2026-07-29); each container = its own lightweight VM (hardware isolation); depends on containerization 0.40.1 | None documented. `container-apiserver` is a **per-user LaunchAgent** + XPC helpers; registry creds in login Keychain (credential-helper still open, #820); SSH-reconnect hangs requiring reboot (#1916); `system start` wedges (#621). Whether it can bootstrap into a system launchd domain at all: **could not verify** | **Secondary/opportunistic** — only on macOS 26 machines with a logged-in user; re-evaluate in 6–12 months. macOS 26 is its floor (macOS 15: no container-to-container networking) |
| **Colima** | v0.10.3 (2026-06-04), pre-1.0, single-maintainer-centric (GitHub Secure OSS Fund funded) | brew-services LaunchAgent (`colima start --foreground`) — login-scoped and flaky (issues #960, #1265); does **not** (verified as of v0.10.3) expose Lima v2.2's LaunchDaemon path | Acceptable sugar on interactive dev machines; don't build the fabric on it |
| **OrbStack** | proprietary | CLI-fully-drivable (`orb`/`orbctl`, docs target headless/CI), Docker-API socket; but per-user lifecycle, GUI needed for auto-update, post-reboot-no-login behavior undocumented | Fine as a *user-selected* backend the agent shells out to; **free tier is personal/non-commercial only — any work use needs Pro $8/mo**; wrong as default |
| **Docker Desktop** | — | Engine stops on logout (docker/for-mac#3567); headless unfulfilled (#6504); paid if org >250 employees or >$10M revenue | **Excluded** |

### Traps checklist

1. **SSH ≠ logged-in user**: SSH sessions land in the Background launchd domain, not Aqua — login Keychain, TCC prompt UI, and GUI-session agents are unreachable. `launchctl bootstrap gui/501 ...` from SSH injects into the console user's live session.
2. **Split the agent**: per-user LaunchAgent for anything needing Keychain/TCC/GUI-adjacent services; root LaunchDaemon only for boot-time VM/network bootstrap (Lima's model). Daemons never get TCC prompts — pre-grant Full Disk Access per-binary or keep I/O in unprotected paths.
3. **Registry auth headless**: avoid Keychain-backed cred stores; use env/file creds or a dedicated programmatically-unlocked keychain.
4. **Bridged networking needs the restricted `com.apple.vm.networking` entitlement** (Apple grants case-by-case). Design for NAT + port-forward; NAT vmnet historically needs root or a root helper (socket_vmnet pattern). `com.apple.security.virtualization` is unrestricted.
5. **Signing**: Developer ID ($99/yr) + hardened runtime + notarization for distributed binaries; TCC grants and Keychain ACLs are per code-signature identity — changing signing identity resets them. All arm64 binaries need at least ad-hoc signing.
6. **Apple `container` wedge states** (#621, #1916): any supervisor driving it needs reboot-tolerant recovery.
7. **Memory ballooning incomplete** in Apple `container` (freed guest memory not returned to host) — capacity accounting caveat.
8. Linux-only isolation (gVisor/runsc, youki/libcontainer) runs *inside* the Lima VM on Mac nodes — plan the runtime-handler plumbing accordingly.

> **Conflict flag — Apple `container` star count:** the Rust brief reports **48.7k stars**; the macOS brief reports **~42–44.5K**. Point-in-time reads disagree; treat as ~40–49k, order-of-magnitude "very popular" either way.
> **Conflict flag — macOS 15 support:** one brief says "full networking requires macOS 26; on macOS 15 all containers share one network" (i.e., degraded-but-works); another says macOS 26 is required and maintainers won't fix non-macOS-26 issues, macOS 15 "semi-supported pre-1.0"; the Rust brief says macOS 15 support "dropped/limited." Net: treat macOS 26 as the floor, but the exact macOS 15 behavior is inconsistently reported.

## 6. Tailscale Integration Plan + Replacement Seam Options

### Integration plan

1. **Node identity & join flow**: control plane holds an OAuth client (scope `auth_keys`, tag-restricted to `tag:svc-*`) → mints ephemeral, pre-authorized, tagged auth keys per node/service via `POST /tailnet/{tailnet}/keys` → feeds `tsnet.Server.AuthKey` (or hands `ClientSecret` directly to tsnet to self-mint). Auth precedence in tsnet: `AuthKey` → `TS_AUTHKEY` → `TS_AUTH_KEY` → OAuth → workload identity federation → interactive.
2. **AuthN on the cluster API**: `LocalClient().WhoIs` per connection gives caller user/node/tags — the built-in authz layer for control-plane RPCs. Tags are service identity (`AdvertiseTags`, `tagOwners` in policy file); tagged nodes don't key-expire.
3. **Service discovery**: Tailscale Services (GA 2026-02-19) — `svc:name` stable MagicDNS names + virtual IPs to healthy backends; tsnet `ListenService(name, ServiceModeTCP|HTTP)` advertises on startup, withdraws on shutdown; hosts must be tagged (`ErrUntaggedServiceHost`). **Limit: 10 services per tailnet including Personal.**
4. **Public ingress**: Funnel only for demos/webhooks (TCP, ports 443/8443/10000, `*.<tailnet>.ts.net` only — custom-domain FR #11563 open; undisclosed bandwidth limits; LE cert rate-limit trap — 34h lockout reported). Real public ingress: Cloudflare Tunnel/Caddy on a VPS that is itself a tailnet node.
5. **Non-Go processes on nodes** (containers, tools): `tsnet.Server.Loopback()` SOCKS5 + LocalAPI, or system tailscaled `--tun=userspace-networking --socks5-server=localhost:1055`.
6. **Plan ceiling awareness**: pricing v4 Personal = free, 6 users, unlimited user devices, **50 tagged resources**, **1,000 ephemeral-resource minutes/month**, 3 ACL groups, non-commercial. Every tsnet service = a tagged device; short-lived per-job tsnet nodes burn ephemeral minutes. **Design choice: long-lived node agents (tagged, ~stable count) with jobs multiplexed over them — not one tsnet node per job.** Ephemeral-minute overage behavior on Personal: unverified. Standard is $8/user/mo.
7. **Rust caveat**: if the agent is Rust, tsnet is unavailable — use system tailscaled + LocalAPI (unix socket HTTP+JSON) and lose in-process WhoIs ergonomics (proxy LocalAPI for identity), or wait on tailscale-rs (experimental, DERP-only, no timeline).

### Replacement seam options (ranked)

1. **Dialer/Listener interface (best, Go)**:
   ```go
   type Fabric interface {
       Listen(network, addr string) (net.Listener, error)
       Dial(ctx context.Context, network, addr string) (net.Conn, error)
       WhoIs(ctx context.Context, remoteAddr string) (Identity, error)
   }
   ```
   Implementations: `tsnetFabric`, `plainFabric` (dev/localhost), future `customRelayFabric`. Wire into `http.Transport.DialContext` / `http.Server.Serve(ln)`. Precedents: Tailscale's own `tsdial`/`netns` dialer interfaces; Coder's `tailnet` package wrapping Tailscale libs at scale. **Critical caveat: put naming and identity behind the seam too** — leaking MagicDNS names, `WhoIs` types, or `svc:` names across it makes the seam cosmetic.
2. **SOCKS5 seam (polyglot)**: everything speaks SOCKS5 to a local endpoint (tsnet `Loopback()` or tailscaled today; your relay later). Weakest identity story.
3. **Control-plane seam**: keep `ControlURL`, key minting, ACL/tag management behind one provisioning module. **Headscale is a live drop-in** (v0.28.0, ~42.6k stars, BSD-3; Tailscale employs a maintainer, publicly endorses it — FOSDEM 2026 "the complementary open source clone"): same tsnet code with `ControlURL` pointed at headscale = fully self-hosted, but **you lose Funnel/Serve and network flow logs**, and must run your own DERP or reuse Tailscale's DERP map. Residual risk is strategic (client-compat tolerance), not legal.
4. **Listener-registration seam** (caddy-tailscale style): config says `listen fabric://svc-name:443`; the binding resolves to tsnet now, custom relay later.
5. **TUN seam (whole-OS)**: real tailscaled + TUN; most transparent, most privileged; replacement cost = a whole VPN implementation. `tsnet.Server.Tun` accepts a custom device if needed.
6. **Full self-owned overlay (escape hatch only)**: wireguard-go (Go) or NepTUN/firezone-boringtun (Rust) — you rebuild key exchange, endpoint discovery, NAT traversal, DERP. Only if Tailscale-the-company dependency becomes unacceptable and headscale doesn't suffice.

## 7. Open Questions → Candidate Decision Tickets

**Language / architecture**
1. **Go vs Rust for node agent + control plane.** Forcing question: is in-process tsnet (with WhoIs authn) a hard requirement? Yes → Go. If tailscaled-via-LocalAPI is acceptable AND Wasm workloads / agent-as-runtime (libcontainer) matter → Rust becomes defensible. A split (Go control plane + Rust agent, or vice versa) is a third option no brief evaluated.
2. **Is Wasm a target workload class for L1?** Determines whether wasmtime/runwasi weight counts in the language decision at all.
3. **Should the L1 agent embed the runtime (libcontainer, Rust-only option) or drive an external engine (containerd/Docker/Lima)?** Affects language, privilege model, and macOS story (embedded runtime is Linux-only regardless).

**L1 / macOS**
4. **Confirm Lima v2.2 LaunchDaemon setup on a real headless Mac** — feature landed but detailed setup docs weren't fetched; exact commands unverified.
5. **Apple `container` adoption trigger**: define the re-evaluation criteria (~6–12 months): headless/system-domain support, keychain-free creds (#820), wedge bugs (#621/#1916) closed. Also resolve the conflicting macOS 15 support reports and star counts (42–44.5k vs 48.7k) if precision matters.
6. **gVisor placement**: which workload classes get runsc-inside-Lima vs plain containers? (Runtime-handler string plumbing through the Lima VM.)
7. **Process supervision for native (non-container) tools on nodes**: no library-grade supervisor exists in either language — design the restart/PTY/log-capture layer explicitly (suture+oklog/run+creack/pty in Go; tokio idioms in Rust).

**L2 / connectors**
8. **Connector wire contract**: adopt interLink's HTTP-plugin shape, track kubernetes-sigs/agent-sandbox's portable-backend proto, or define a custom one? (All briefs converge on out-of-process; the question is which schema.)
9. **Capacity model schema for elastic providers**: how do price/rate-limit/quota/concurrency-tier dimensions surface to the deliberately-dumb scheduler without recreating Nomad #10549?
10. **Provider shortlist for v1**: Daytona (REST+OpenAPI+Go SDK, self-serve) and Fly Machines (REST+leases+cheap idle, but BYO exec agent) are the two clean fits; E2B (best pause/resume, TS/Py only) and Modal (Go SDK beta, gRPC-only) are second tier; Vercel (best idle billing, single region, SDK-gated); Cloudflare requires a Worker shim — include at all? **Ona: explicitly out** (Enterprise-gated API + OpenAI absorption). Note the two briefs' rankings differ in scope (one excludes Daytona) — reconcile into one warpweft-specific ranking.
11. **Fly in-VM exec agent**: if Fly is in, warpweft must ship its own daemon in the image (Fly `exec` is 60s/buffered/no-background). Is that the same binary as the L1 node agent? (Attractive convergence.)
12. **Snapshot/pause semantics in the contract**: experimental features (Daytona `_experimental_create_snapshot`, Modal memory-snapshot alpha, Fly best-effort suspend) — gate behind capability flags or exclude from v1?
13. **Verify before building**: Daytona license (AGPL claim unconfirmed), Daytona preview-URL WebSocket passthrough, Modal REST fallback existence, Vercel raw REST stability, whether OpenAI–Ona closed.

**L3 / app layer**
14. **Queue substrate**: Windmill-style Postgres pull-queue (tags→worker groups) vs pushing through the cluster API — does L3 own a queue at all, or is the L1 API the only dispatch path? (Prior art says control planes keep their own queue separate from compute.)
15. **How much SSSF to adopt**: phases/envelopes/gates/warm-retry as L3's workflow model, vs a thinner Temporal-UI-style pure control surface over L1. Also: SSSF's exact publish date/commit history unverified; Claude Code harness still "stubbed."
16. **Agent-facing API shape**: Devin-style `POST /sessions` (prompt + limits + structured_output_schema + tags) as the north star for what AI agents call?
17. **Reuse vs build for the coding-agent execution layer**: sandcastle's provider interface is a candidate integration point (write a warpweft provider) — but it's pre-1.0, single-maintainer, 5.5 weeks quiet, 126 open issues. Adopt-and-pin, fork, or steal patterns only?
18. **Dokploy stack conflict** (Drizzle+tRPC per official docs vs Prisma/Material-UI per a secondary source) — only matters if using it as a reference implementation; official docs say Drizzle.

**Networking**
19. **Tailscale plan ceiling**: does the fabric fit in Personal's 50 tagged resources + 1,000 ephemeral minutes/month + 10 Services, given "non-commercial use" terms and warpweft touching work projects? Decide: Personal / Standard $8/user/mo / headscale from day one. Ephemeral-minute overage behavior: unverified.
20. **Seam discipline ticket**: define the `Fabric` interface (incl. naming + identity) before writing the first tsnet call, so the headscale/custom-relay path stays real.
21. **Headscale trade**: self-hosting loses Funnel/Serve — does anything in the design depend on Funnel? (If public ingress goes through a fronting VPS anyway, the answer is likely no.)
22. **tailscale-rs watch item**: revisit if/when it gets NAT traversal + 1.0 (no timeline upstream) — would unlock the Rust-agent-with-embedded-mesh option.

**Explicitly flagged conflicts (do not smooth over)**
- Apple `container` GitHub stars: 48.7k (rust brief) vs ~42–44.5K (macOS brief).
- Apple `container` on macOS 15: "shared single network, works" vs "semi-supported, maintainers won't fix" vs "dropped/limited" — three phrasings across briefs.
- Dokploy ORM: Drizzle+tRPC (official docs) vs Prisma/Material-UI (secondary source).
- Sandbox-backend ranking: sandbox-providers brief ranks Fly #1 (Daytona out of scope); ona-daytona brief calls Daytona the strongest overall connector fit — different comparison sets, needs one reconciled warpweft ranking.
- Factory.ai pricing: "not in the post" (software-factory brief) vs "~$20/$100/$200/mo tiers" (app-layer brief, secondary sourcing).
- Bloop/Vibe Kanban shutdown (~April 2026): single secondary source only.
