# M3 ratified-spec draft: `kind=oci`

## Spirit

Wefty should make “run this in a container” feel like a property of the work, not a second product. The same echo payload can run as a `class=one-shot` job or a `class=service` job, and the operator chooses its isolation with `kind` alone. A Linux node uses its native engine and a Mac uses Lima, but those are node-local mechanics: the cluster still sees one node, one job queue, one history, and one command family for service-class jobs.

The safety promise is deliberately narrower than Kubernetes and stronger than “we started a container.” M3 provides a named runc isolation profile for semi-trusted work on machines the user owns, binds every payload to current attempt authority, and proves cleanup before claiming a machine is clean. Availability may yield to hygiene; stale containers are reaped, never adopted, and an engine that disappears makes the node ineligible before it can receive more OCI work.

> **Status:** ratified by the owner 2026-08-22 (spirit-level skim; cross-model reviewed by Opus 5 and Codex). This folds the owner resolutions of #102, #103, #104, and #106–#113 into one contract/mechanics/acceptance document in the #57 pattern. The owner chose #128 as the first OCI hardware acceptance lane on 2026-08-22; its evidence still gates the unconditional headless guarantee. The default per-node cache ceiling delegated by #107 was ratified by the owner at 16 GiB on 2026-08-22; no owner call remains.

## 1. Contract

### 1.1 Workload identity and payload source

`JobSpec.kind` remains the open isolation discriminator. `process` keeps the existing flat `execution.executable`, `argv`, and host `working_directory`; `oci` requires `execution.oci` and forbids those process-only fields. `JobSpec.class` remains the independent lifecycle clock (`one-shot` or `service`). Neither axis implies the other. (#106 M3)

The OCI arm is:

```text
execution.oci {
  image { reference, digest }
  argv[]
  working_directory
  mounts[] { node_path, container_path, read_only }
  limits { memory_bytes, cpu_millicores }
}
```

- `reference` is a repository plus optional tag and never embeds `@digest`; `digest` is `sha256:` plus 64 lowercase hexadecimal characters. `digest` may be absent only on an initial one-shot submission. It is required for service-class jobs, saved image Workflow versions, and every one-shot dispatch after the first successful resolution. Together the fields execute `reference@digest`, while the tag remains provenance. (#106 M3)
- `argv`, when present, is a full-vector replacement applied after image config and contains at least one non-empty element. There is no separate entrypoint override in M3. `working_directory` is a container path and defaults to the image value. (#106 M3)
- `env` and `sensitive_env` remain shared fields. A container starts from image environment only, then applies `env`, `sensitive_env`, and finally authoritative wefty-reserved values. Every pre-existing **reserved** key is stripped from image and operator environment before injection; other tenant-defined `WEFTY_*` keys are not reserved implicitly. As amended by the agent-computer spec §11 item 6, the exact reserved-name set is `WEFTY_HANDOFF_DIR`, `WEFTY_SERVICE_DIR`, `WEFTY_SERVICE_PORT`, `WEFTY_L3_ENDPOINT`, `WEFTY_RUN_TOKEN`, `WEFTY_COMPUTER_TOKEN`, `WEFTY_COMPUTER_VIEW_PORT`, and `WEFTY_COMPUTER_CONTROL_PORT`; this declaration does not itself inject the three Computer values. The host agent environment is never inherited. (#106 M3; #109 M3; #125 agent-computer; #126 agent-computer)
- Optional OCI `memory_bytes` and `cpu_millicores` are cgroup-v2 hard limits. Their absence means uncapped, as for native process work today. They are admission requirements, not a QoS policy. (#109 M3)
- `runtime_handler` remains reserved and open. Empty means the configured default (`io.containerd.runc.v2` in M3); a non-empty value requires the corresponding node capability. `runsc` is reserved but not delivered. (#102 research; #109 M3; #110 M3)

Every structural rule is implemented both in the JSON Schema/OpenAPI surfaces and `contract.ValidateJobSpec`; L1 never relies on schema validation performed by a caller. Existing process specifications remain valid. (#106 M3)

### 1.2 Image programs in L3 and the CLI

L3 stores an immutable typed program snapshot rather than persisting an L1 `JobSpec`. Its image arm contains the full program configuration: `reference`, `digest`, `argv`, container `working_directory`, mounts, kernel limits, and `runtime_handler`. Every dispatch and rerun copies those fields without defaulting or re-resolution; only attempt-local reserved environment, authority, paths, ports, and bridge values are injected later. Saved image Workflows exist through the L3 API in M3 and always carry a digest. (#106 M3)

`wefty submit` accepts exactly one source among `--workflow-ref`, `--script`, and `--image`; `--argv` and repeatable `--mount NODE_PATH:CONTAINER_PATH[:ro]` apply to images. `wefty services create` adds the same image arm without creating a new command family and resolves tag→top-level digest with a registry HEAD before submission; L1 still rejects a service-class job without that digest. (#106 M3)

An operator mount makes the work Pinned. CLI, L3, and L1 each require exactly one stable-node routing tag (or `--node NODE_ID`) whenever a mount exists; no layer infers the submitting node. The selected node revalidates every source path immediately before use. (#106 M3; #109 M3)

An image-based one-shot job resolves once at its first launch and persists the resolution through a fenced, write-once observation. That job-level identity is copied into every later attempt, pre-start retry, and rerun; none may re-float the tag. A rerun whose source job failed before resolution is rejected with `no_resolved_image_snapshot`. Service-class jobs must already contain a top-level digest at create time; changing an image means creating a new service-class job. (#106 M3; #108 M3 clarified by #106)

### 1.3 Attempt evidence and result truth

Image evidence records submitted reference, top-level digest and media type, nullable index digest, selected platform-manifest digest, canonical OCI platform including variant, effective runtime handler, snapshotter, `resolved_at`, and `started_at`. The runtime platform comes from the OCI probe, never the Darwin identity of a Mac host. (#108 M3)

L1 gains a fenced, idempotent start acknowledgement. Resolution, pull/import, unpack, spec construction, and `Wait` registration occur while the attempt remains `claimed`; only the authoritative helper `Started` event after successful task start permits an OCI attempt to become `running`. L1's existing implicit promotions on first renewal, first authoritative log, and successful completion are all kind-gated away for OCI; those operations may record their own facts but never substitute for `Started`. (#108 M3; #111 M3)

`ProcessResult` gains a mutually exclusive `runtime_failure {code, message}` arm. Pre-`Started` failures remain coded `spawn_error` values such as `runtime_unavailable`, `image_unavailable`, and `oci_spec_rejected`; post-`Started` helper or engine loss is `runtime_failure`, never a fake signal or spawn error. The explicit service-readiness exception is `startup_readiness_timeout`: its deadline begins after authoritative OCI `Started`, but it remains a restartable `spawn_error` because the service never became publishable. OOM is additive evidence and is not inferred from exit 137. (#110 M3; #111 M3; #112 M3)

For a one-shot pre-start `runtime_unavailable`, L1 terminalizes the old attempt with coded pre-start evidence and atomically revokes its authority while moving the job `claimed → queued`. The job retains one persisted, agent-flag-tunable pre-start infrastructure budget (default ten minutes) and capped exponential backoff across attempts; replay cannot mint another retry, and exhaustion is terminal. Mid-run runtime failure is terminal and requires an explicit L3 rerun. Service-class jobs requeue on pre- or post-start runtime loss on the bound node, preserve their restart streak, and wait for capability recovery. Permanent image errors, exhausted pull/pre-start budgets, and all codes absent from the explicit classifier table are terminal for one-shots and latch service-class jobs by default. (#106 M3; #108 M3; #110 M3)

## 2. Isolation profile and networking

### 2.1 Wefty v1 isolation profile

M3 names and serializes one profile rather than promising vague “Docker-like” isolation. Golden fixtures start from containerd v2.3.4's generated Linux spec and apply the following explicit rules; a containerd patch upgrade regenerates and reviews the fixture rather than silently inheriting new defaults. (#102 research; #109 M3)

- Run as the image `USER`; empty means `0:0`. There is no user-namespace remap tier in M3. Named users and supplemental groups are resolved guest-side from the pinned image. (#104 prototype; #109 M3; #111 M3)
- Set all five capability sets explicitly to Docker's default 14 minus `CAP_NET_RAW` and `CAP_NET_BIND_SERVICE`. Set `no_new_privileges=true`. (#109 M3)
- Generate containerd's default seccomp profile guest-side after architecture, kernel, and capability resolution; handle `clone3` with the profile's `ENOSYS` behavior. AppArmor is applied opportunistically where present but does not affect M3 placement. (#109 M3; #110 M3)
- Use private PID, IPC, UTS, mount, and cgroup namespaces; masked/read-only proc paths; deny-all device cgroup; only OCI pseudo-devices; no privileged mode or host-device passthrough; writable root filesystem. (#109 M3)
- Use explicit `io.containerd.runc.v2`, `overlayfs`, the `wefty` containerd namespace, immutable digests, and deterministic resource names. Auto-selection is forbidden because the prototype selected unavailable `erofs` and the wrong runtime. (#104 prototype; #108 M3; #111 M3)

Serialized-spec fixtures on native Linux and Lima arm64 are part of acceptance; profile construction belongs to the privileged helper because it depends on guest files and kernel facts. (#104 prototype; #109 M3; #111 M3)

### 2.2 Shared node networking

OCI payloads share the node network namespace: the Linux node's namespace natively and the Lima guest's namespace on a Mac. Outbound access is open. The Fabric front door is the only **supported** inbound path, but M3 does not claim enforced inter-job network isolation; a payload can bind another free high port. (#109 M3)

The helper applies resolver configuration and `/etc/hosts` explicitly; shared networking does not imply correct name resolution. (#109 M3)

The helper allocates attempt-scoped ports from a reserved range and holds the reservation until the payload binds. OCI service-class payloads must bind the injected port on loopback; `0.0.0.0` is forbidden because it bypasses the front door in a shared namespace. The agent's kind-independent Fabric listener proxies through an opaque `serviceRuntimeEndpoint` supplied by the runtime adapter. (#109 M3; #112 M3)

Lima dynamic TCP/UDP forwarding is disabled. Readiness and Fabric front-door traffic are host→guest and use the helper's fenced `DialAttemptPort(attempt identity, port)` stream; it is not a general guest dialer. Linux uses the same logical tunnel contract for service-class payloads. Every agent listener is authenticated or Unix-socket-only. (#109 M3; #111 M3; #112 M3; #113 M3)

For one-shot runs, `WEFTY_L3_ENDPOINT` exposes only the run-scoped bridge and must be reachable for the attempt lifetime. Linux keeps the loopback bridge. On Mac, inject `host.lima.internal` or the discovered Lima host gateway, never a hard-coded `192.168.5.2`, and bind the host bridge only to a Lima-reachable non-LAN surface, never `0.0.0.0`. If macOS cannot bind such a surface, use a constrained guest→host helper reverse tunnel as the fallback. That direction is not covered by #111's current RPC list, so the helper-protocol ticket must add an attempt-authorized `DialHostBridge`-style verb before the fallback can ship. `WEFTY_RUN_TOKEN` authorizes requests but does not isolate the listener from sibling attempts on the node. (#103 research; #106 M3; #109 M3; #111 M3)

### 2.3 Mount authority

A bare OCI job sees only its image and wefty-injected mounts. Operator mounts are writable by default and `:ro` opts into recursive read-only behavior with private propagation. A writable mount delegates write authority over exactly that tree, including the possibility of root-owned files on Linux. (#101 map; #109 M3)

Node-side and guest-side validation require an absolute source beneath configured allowed roots; reject root, socket paths, symlinks in any component, sockets/devices/FIFOs, and targets equal to, containing, or contained by a reserved target after normalization. A Mac source must translate into the preconfigured Lima mount root and pass the same guest-side checks. (#109 M3)

Operator bind sources are external. Removal records their handles but never traverses or deletes them. (#106 M3; #109 M3; #111 M3)

## 3. Capability scheduling

One deep `RequiredCapabilities(JobSpec)` module derives a normalized set at job creation and persists it transactionally. It emits `kind:<name>`, `runtime_handler:<name>`, and `cgroup_v2` when kernel limits are requested; `apparmor` is observed hardening, not an M3 requirement. The atomic claim `UPDATE` anti-joins requirements against the node's current capabilities, and diagnostics reuse the same module. (#110 M3)

Capabilities are eligibility, never capacity. Slots remain class-scoped, and a capable node still needs the proper one-shot or service slot. (#110 M3; CONTEXT.md)

The agent earns `kind:oci` only by creating, starting, waiting for, and cleaning a tiny local probe image under the v1 profile within ten seconds. It probes at startup, every heartbeat, and on runtime events; each advertised runtime handler is probed independently. The probe image is preloaded locally and exempt from cache eviction so registry health cannot masquerade as engine health. (#110 M3; #107 M3)

Registration and every heartbeat carry a boot-scoped capability revision and the complete set. Higher replaces atomically; equal plus identical is replay; equal plus different conflicts; lower refreshes liveness but cannot alter capability state. Replacement, capacity refresh, and liveness update share one L1 transaction. Capability updates never touch durable `claims_enabled`. Every agent call path reads one capability-state module rather than a startup snapshot. (#110 M3)

One failed probe immediately disables local OCI admission; the next successful heartbeat publishes a higher revision that withdraws the badge. Running attempts continue until positive task/helper/engine death evidence arrives. Recovery publishes only after helper handshake, the boot barrier, and a fresh successful probe. L1 retains bounded sanitized observation metadata containing revision, observed time, missing capabilities, and one stable reason code; full diagnostics remain node-local. (#110 M3; #111 M3)

## 4. Image identity, delivery, and cache

### 4.1 Resolve once, stick, record

Service-class jobs store the top-level digest at creation. At first binding, they select and durably pin the platform manifest against the probed OCI runtime platform; every restart copies that identity into attempt evidence. A one-shot job resolves once at first launch, persists that job-level write-once identity, and copies it into every later attempt/retry/rerun; tag movement after the first resolution has no effect. (#106 M3; #108 M3 clarified by #106)

The later #111 topology governs: the helper executes `EnsureImage` and every containerd call. The agent owns classification, retry, backoff, and the total budget but does not become a raw containerd client. Public registries are the only registry path in M3. (#108 M3 amended by #111 M3)

Transient network, DNS, 5xx, and 429 failures retry with backoff and `Retry-After` under one total ten-minute budget, tunable by agent flag, covering resolution, fetch, unpack, and waits. Not-found, invalid manifest, and unsupported platform fail immediately. The agent-local `pulling` phase consumes the attempt and slot but not payload max-runtime or service readiness time. (#108 M3)

`wefty node load-image FILE` verifies descriptors and recomputed digests, imports into the fixed namespace, admits the probed platform, and returns top-level and platform digests. Same-digest replay is idempotent; a same-name collision with different bytes fails. (#108 M3)

### 4.2 Four holds and bounded cache

Image lifetime has four distinct holds: a shared operation lease around pull/import/unpack, a live-attempt pin, a durable service-binding pin, and an evictable node-cache entry. Singleflight is keyed by namespace, top-level digest, runtime platform, and snapshotter; leader cancellation does not cancel shared work, and every waiter attaches its own pin before the operation lease releases. (#108 M3)

**Default cache ceiling: 16 GiB (owner-ratified 2026-08-22).** #107 delegated the exact number to this spec. Whatever value wins is operator-tunable by agent flag and accounted from containerd content-store usage in the `wefty` namespace. Never evict the probe image, an active attempt's image, or a bound service's image; evict oldest-unused entries after pulls and periodically until within the cap, recording digest, reason, and bytes. (#107 M3)

Boot reconciliation reads a durable agent-local binding-pin ledger and reconciles it against L1 before eviction starts; this requires no new L1 protocol field. A wiped cache reacquires pins and repulls under the normal budget; failure latches the service-class job instead of crash-looping. Removal releases the binding pin but does not delete cached image content. (#107 M3; #108 M3; coordinator selection)

## 5. Runtime topology

### 5.1 One node, one unprivileged agent, one privileged helper

A Mac remains one node; its Lima VM, containerd, and containers are plumbing. Linux uses the same topology. The agent runs unprivileged and all containerd traffic goes through a root-owned, stateless, narrow helper: `EnsureImage`, `Run`, `Signal`, `Watch`, `Delete`, `Verify`, `Sweep`, and fenced `DialAttemptPort`. The raw containerd socket is root-only and never forwarded to the host agent. (#111 M3; #113 M3)

The helper is the agent binary's private `__wefty_oci_helper` mode. Linux installs it as a systemd socket-activated root service with `SocketMode=0660`, `SocketUser=root`, and `SocketGroup=wefty-oci`; the agent unit uses `SupplementaryGroups=wefty-oci` and is restarted after group changes rather than assuming live pickup. Mac setup copies the matching Linux build into Lima and forwards only its `0660 root:wefty-oci` socket to an operator-owned `0700` host path. A major-version or checksum mismatch suppresses OCI capability. (#111 M3; #113 M3)

### 5.2 Guardian equivalence and boot barrier

The helper issues one exclusive opaque session capability, authenticates the peer, and enforces helper-monotonic heartbeats. Each attempt deadman is refreshed only after a successful L1 lease renewal. EOF alone is insufficient because a hung connection can remain open. Loss of the session reaps every attempt owned by that agent boot. (#111 M3)

Before OCI can be advertised, one serialized boot barrier authenticates and version-handshakes the helper, takes exclusive ownership, sweeps **all** resources in the `wefty` namespace, verifies absence, resumes pending removals, runs the functional probe, and then publishes a fresh capability revision. No survivor is adopted, even if a boot ID was reused. A helper restart performs the same sweep before accepting a session. (#111 M3; ADR-0003)

Create and label a per-attempt containerd lease before any other resource. Every enumerable resource carries node, job, attempt, fencing token, boot session, class, and removal generation labels; creation is serialized against sweep. (#111 M3)

`WorkloadRuntime` is an agent-owned runtime-neutral seam selected by `kind`. It accepts attempt authority, `JobSpec`, limits, managed resources, and started/readiness hooks, and returns a structured result plus `ReapAndVerify`. The current process runner becomes the process adapter; executable materialization moves inside it, while the Mac process Guardian remains unchanged. (#111 M3)

### 5.3 Logs and finalization

The helper attaches shim-side `binary-v2` logging and writes append-only, per-stream framed segments containing sequence, byte count, and checksum. On Mac those segments cross through a wefty-owned shared-mount directory; this is deliberately different from service data volumes, for which #112 rejects virtiofs as a persistence dependency. The agent tails segments into the existing `OutputSink`, acknowledges them, and allows rotation only after acknowledgement; forced eviction emits an exact gap. A lost or truncated segment seals evidence incomplete. Logs never share the Guardian heartbeat stream. (#102 research; #104 prototype; #111 M3; #112 M3)

Normal exit, signal initiator, OOM evidence, pre-start failure, and post-start runtime failure produce exactly one result arm. A known signal carries exactly one termination cause (`Agent`, `Guardian`, or `Spontaneous`); OOM remains additive evidence. Runtime task/container/snapshot cleanup and log finalization complete before L1 makes the attempt eligible again. (#111 M3; #112 M3)

## 6. OCI services

An OCI service-class job keeps its binding's published Fabric port, top-level digest, selected platform manifest, and service data volume across restarts. Every crash restart and stop→start creates a fresh attempt, container, task, backend port, and writable root snapshot from the pinned image. Runtime-native restart is disabled. (#106 M3; #112 M3)

The helper allocates the backend port per attempt in a bounded named endpoint map (`service` for an ordinary portful service; exactly `view` and `control` for the ratified Computer extension) and returns an opaque dial function keyed by name. The generic service Guardian probes the ordinary `service` path agent-side, so readiness covers payload, helper session, and tunnel. The Computer-specific dual-WebSocket readiness contract remains owned by the agent-computer extension. The startup deadline begins at successful spawn; after first readiness, loss withdraws forwarding, severs every established front-door tunnel before publishing withdrawal, does not kill the payload, and uses the existing recovery hysteresis. (#112 M3; #123 agent-computer; #125 agent-computer)

A portless OCI service-class payload has no endpoint, probe, publication, or readiness field and becomes `running` at authoritative `Started`, after `Wait`, logging, and session ownership are established. Its binding still occupies a service slot. (#112 M3)

Only `/wefty/service` (`WEFTY_SERVICE_DIR`, from §1.1's reserved set) persists for a service-class job. Its helper-owned guest-native volume is created fresh per job, initialized once to the image's resolved UID:GID, and never re-chowned on restart. On Mac it is intentionally not Finder-visible. A replacement service-class job gets fresh data even for the same digest; cross-version continuity requires an explicit operator bind mount. (#112 M3)

One-shot jobs receive `/wefty/handoff` (`WEFTY_HANDOFF_DIR`, from §1.1's reserved set) using the existing handoff lifecycle. Neither injected source path leaks into the payload. Reserved targets cannot be shadowed. (#106 M3; #112 M3)

Stop performs TERM, grace, KILL if needed, and positive runtime quiescence; it releases the slot but retains the binding, digest pin, and service data. Start transitions through `queued` and reacquires service capacity before creating a fresh attempt. Failure to prove quiescence latches `failed`. Runtime loss preserves data and blocks replacement until the boot barrier proves stale resources absent. (#112 M3)

## 7. Removal proof

OCI removal extends the existing managed-root protocol; it does not create a parallel cleanup state machine. **Acknowledgement strictly follows deletion:** persist the immutable runtime-resource manifest and removal intent → withdraw publication and close the front door → reap and verify all attempt runtime resources → purge spool/evidence material owned by the agent → quarantine, delete, and verify helper runtime/log/data directories → release the binding image pin → attest `agent_cleaned`. (#111 M3; #112 M3; ADR-0002)

The manifest names the job, removal generation, every attempt lease/task/container/snapshot/cgroup/log directory, and wefty-injected volume. `NotFound` counts only after identity matches the recorded job and generation and the compound absence proof succeeds. The existing prepared → quarantined → complete crash-resumption phases remain authoritative. (#111 M3; #112 M3)

Removal from running, stopped, failed, backoff, and offline states is idempotent. Offline reads `removal_pending`; `forget --force` waives proof but leaves the deletion directive standing. Bind sources are never traversed or deleted, and cached image content is not part of the proof. (#111 M3; #112 M3)

Success proves task, container, writable snapshot, attempt lease, shim/cgroup state, framed logs, handoff/service data, runtime directories, and attempt spool records absent; publication and process/port liveness are absent; sensitive environment is scrubbed; the operator working directory and bind sources remain byte-for-byte untouched. (#112 M3)

## 8. Bootstrap, doctor, and OCI intent

### 8.1 Installation and setup

Prerequisites are Lima ≥2.2 with `vz` on macOS, or containerd ≥2.0 plus runc 1.x and overlayfs on Linux. The tested range is Lima 2.2.0, containerd 2.3.x, and runc 1.5.x. Minimum failures are hard errors; versions outside the tested range warn. CNI is not installed. (#103 research; #104 prototype; #113 M3)

`scripts/install-oci-deps.sh` installs prerequisites only through Homebrew or named Debian/Ubuntu/Fedora releases, adds no third-party repository, refuses unknown platforms, and never changes wefty configuration. `wefty node setup-oci` configures but never installs; missing prerequisites cause a no-op with an exact runbook pointer. Successful setup installs and pins the local probe image but preserves an existing disabled OCI intent. (#110 M3; #113 M3)

Local singular commands (`wefty node setup-oci|doctor|oci start|oci stop|load-image`) resolve the installed node configuration before Fabric initialization and talk to the live agent through an operator-only Unix control socket. The agent is the sole writer of local intent and runtime state. (#108 M3; #113 M3)

### 8.2 Durable OCI intent and Mac supervision

OCI intent is a revisioned, durable, node-local `enabled` bit. `oci stop` persists disabled first, disables local admission, publishes capability withdrawal without waiting for L1, withdraws services, reaps attempts, and then stops Lima on Mac; Linux leaves containerd running. `oci start` persists enabled, restores helper transport, runs the boot barrier and probe, and only then advertises. Setup never re-enables an intent the operator disabled. (#111 M3; #113 M3; ADR-0004)

On macOS the operator-user agent is launched at system boot by `dev.wefty.agent`, a system LaunchDaemon with absolute paths and explicit `HOME`, `LIMA_HOME`, `USER`, `LOGNAME`, `PATH`, and working directory. The agent is the only Lima supervisor; Lima's own autostart unit is absent. It starts or repairs Lima only while OCI intent is enabled, handles `Broken` with bounded `stop --force` recovery, and degrades to process-only rather than crash-looping. (#103 research; #113 M3)

**VM sizing (Mac).** The Lima VM's memory is a fixed reservation set at `setup-oci` time, never computed live. Default: **25% of host RAM, capped at 4 GiB** (owner-ratified 2026-08-22); CPU default 4 vCPU capped at half the host's cores; disk 32 GiB. All three are operator flags (`--vm-memory`, `--vm-cpus`, `--vm-disk`); changing them later is a restart-required template change (`--apply-restart`). `doctor` reports the configured reservation. Per-job limits inside the VM are separate and opt-in (§2.1). (#113 M3; owner 2026-08-22)

Template convergence is classified as live-safe, restart-required, or recreate-required. Restart requires `--apply-restart`; recreate requires `--recreate`, explicit confirmation, and zero live OCI attempts. An unchanged rerun causes no restart, intent bump, or capability revision. (#113 M3)

### 8.3 Doctor

`wefty node doctor` is facts-only and has matching versioned JSON and human views: host and runtime platforms, agent user and launch unit, Lima state, containerd/runc/helper versions, helper handshake, last probe verdict/age/revision, OCI intent, cache bytes/cap/last eviction, and allowed mount roots. It reads the same recorded probe facts used by heartbeat and setup; it never performs setup or restarts anything. (#110 M3; #113 M3)

M3's stable not-advertising reason codes are: `oci_intent_disabled`, `prerequisite_missing`, `runtime_version_unsupported`, `helper_unreachable`, `helper_unit_unavailable`, `helper_version_mismatch`, `helper_handshake_failed`, `boot_sweep_failed`, `probe_failed`, `lima_stopped`, `lima_broken`, `lima_start_timeout`, `template_restart_required`, `template_recreate_required`, `mount_root_unavailable`, and `local_permission_denied`. Doctor may attach sanitized local detail; L1 stores only the code, observation time/revision, and missing capability set. Unknown local failures collapse to `probe_failed`, not a new ad-hoc string. (#110 M3; #113 M3; #298)

Paths and raw errors remain node-local and sanitized. Units, plist arguments, doctor output, logs, and L1 reasons contain no tsnet credentials. “Headless” means after FileVault unlock and OS boot with no GUI login or SSH; no Mac daemon can run before startup-volume unlock. (#113 M3)

## 9. Acceptance

### 9.1 Artifact and lane rules

`cmd/wefty-echo-service` gains `--once`. The same multi-arch Linux image supports both classes: one-shot mode uses §1.1's `WEFTY_HANDOFF_DIR`, `WEFTY_L3_ENDPOINT`, and `WEFTY_RUN_TOKEN`, makes one authenticated bridge request without logging its token, emits distinct stdout/stderr markers, and exits zero; service-class mode uses `WEFTY_SERVICE_PORT` and `WEFTY_SERVICE_DIR`, binds loopback, serves health/echo with PID evidence, and handles TERM gracefully. (#106 M3; #107 M3)

CI builds `linux/amd64` and `linux/arm64`, publishes public `ghcr.io/derek-x-wang/wefty-echo-service` on main by commit tag, records the index digest, and emits an OCI tarball artifact. Tests consume only the digest. There is no blessed base image; an illustrative, non-product-owned Dockerfile lives under `examples/`. (#107 M3)

Every implementation ticket extends the existing `service_acceptance` suite. Linux-native OCI coverage also grows through the main/weekly `service-acceptance-realtiming` workflow, with containerd ≥2.0, runc, and overlayfs provisioned explicitly on `ubuntu-latest` by the first real-engine ticket. GitHub-hosted `macos-15` Apple-silicon runners cannot boot nested Lima `vz`, so Mac/Lima coverage runs only in the attended owner-hardware #128 family through a `docs/acceptance/` runbook and the `service_acceptance` tag; it is never claimed by the realtiming workflow. A unit-test-only runtime capability is not complete. The realtiming lane remains evidence rather than part of `all-tests-pass`, preserving its current contract. (#101 map; #113 M3; #114 destination; #128 prototype)

The owner chose #128 as the first OCI hardware acceptance lane on 2026-08-22. It must prove a cold-rebooted Mac returns with a fresh OCI capability revision after FileVault unlock, without GUI login or SSH, and recover from hostagent loss and Lima `Broken`. Its PASS verdict gates ratification of the headless promise and Mac rollout, but not the portable contract or native-Linux work. (#101 map; #113 M3; #128 prototype)

## 11. Proposed `CONTEXT.md` vocabulary patch

Do not apply this block mechanically until the owner ratifies the spec. It adds only terms that carry durable cross-ticket meaning.

```diff
 ### Scheduling and execution (L1, the cluster)

+**Capability revision**:
+A boot-scoped monotonic revision over a node's complete observed capability
+set. Only a higher revision can replace the set within that boot session.
+_Avoid_: capability version, feature flag, health generation
+
+**OCI intent**:
+The revisioned node-local operator decision that the OCI runtime is enabled
+or disabled. Capability reports what the node can do now; OCI intent records
+whether the agent is allowed to make it available.
+_Avoid_: runtime status, capability toggle, autostart preference
+
+### Node runtime (the agent)
+
+**OCI helper**:
+The narrow, root-owned node-local adapter that constructs OCI specs, talks
+to containerd, enforces boot-session lifetime, and proves runtime cleanup.
+It owns mechanics, never scheduling, leases, restart policy, or operator
+judgment.
+_Avoid_: containerd proxy, sidecar, runtime daemon, using "shim" (a
+containerd term) for the wefty helper
+
+**Boot barrier**:
+The serialized OCI takeover that authenticates the helper, sweeps all stale
+wefty runtime state, verifies absence, resumes pending removals, probes the
+runtime, and only then permits capability publication and claims.
+_Avoid_: adoption, reconciliation window, best-effort cleanup
+
+**Isolation profile**:
+A named, versioned set of OCI process, namespace, capability, seccomp,
+device, mount, and networking rules. In M3, `kind=oci` selects the wefty v1
+isolation profile.
+_Avoid_: Docker-equivalent, sandbox tier (unless naming an actual tier),
+container defaults
+
+**Service data volume**:
+The helper-owned, guest-native `/wefty/service` storage that belongs to one
+`class=service` job, survives that job's attempts, and is deleted with that
+service-class job.
+_Avoid_: working directory, bind mount, container writable layer, shared
+volume
```
